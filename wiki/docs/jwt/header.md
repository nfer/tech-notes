# header 与签名算法

> 一句话：header 只说明「这段 token 用了什么保护」，其中最关键的 `alg` 是**攻击者可控的输入**，必须由服务端按白名单判断，不能照它说的用。

## header 里有什么

header 是 JOSE Header，描述签名和加密用了什么参数。JWS 形式下常见三个字段：

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `alg` | 是 | 签名算法标识 |
| `typ` | 否 | 声明的媒体类型 |
| `kid` | 否 | 用的是哪把密钥 |

除此之外还可能看到 `jku`、`x5u` 这类指向公钥地址的字段，日常登录场景很少用。

## alg：唯一必填的字段

RFC 7515 对它的要求很硬：**必须存在，且实现方必须理解并处理它**。取值要么来自 IANA 的算法注册表，要么是一个不含冲突的名字。

常见的几类值：

- `HS256` / `HS384` / `HS512`：HMAC + SHA，对称密钥，签发方和验证方持有同一把；
- `RS256` / `RS384` / `RS512`：RSA 非对称，私钥签、公钥验；
- `ES256` / `ES384` / `ES512`：椭圆曲线非对称；
- `none`：**不签名**。

`none` 是标准里明确存在的值——RFC 7519 用它定义「无保护 JWT」（Unsecured JWT）：`alg` 写 `none`、签名段留空。这类 token 的任何内容都没有完整性保护，等于把 claims 直接交给持有者填写。

## alg 必须由服务端决定

`alg` 在 token 里，而 token 由客户端持有——**它是一份攻击者可以随意修改的输入**。

如果服务端按 token 里写的算法去验证，攻击者只要把 `alg` 改成 `none`，并清空签名段，就能让一个伪造身份通过校验。这类漏洞在真实系统里反复出现过，根源都是「用输入决定验证方式」。

正确做法是反过来的：服务端先定下自己接受哪些算法，再拿这个集合去过滤 `alg`；集合之外一律拒绝。签发时同理，算法由签发方指定，不读调用方传来的值。

## typ 和 kid

`typ` 声明媒体类型，通常就是 `JWT`。它的作用是在「同一份数据里可能混有多种结构」时做区分，实现方可以选择忽略它。所以 `typ` 不是安全边界，不能指望靠它拦住「把别的类型的签名拿过来当 JWT 用」。

`kid` 是一个提示，告诉验证方该用哪把密钥，结构没有规定，通常是密钥的 id 字符串。它真正的价值在多密钥场景：轮换期间新旧两把钥匙同时可用，验证方靠 `kid` 挑对应的公钥。

注意 `kid` 也一样来自 token，如果实现拿它拼文件路径或查数据库，就可能被注入——用之前必须校验格式，并且只在自己已知的密钥集合里查。

## 改 header 也必须重签

header 和 payload 一样在签名输入里，签名覆盖的是 `base64url(header) + "." + base64url(payload)`。所以改 header 里任何一个字段，签名都会失配——攻击者想改 `alg` 或 `kid`，不能只改 header 就完事。

## 常见误区

- ❌ 按 token 里的 `alg` 选验证算法 → 攻击者写 `none` 直接绕过签名。
- ❌ `alg` 只有算法名，没有攻击面 → 它是最典型的「不可信输入」。
- ❌ `typ` 能防止类型混淆 → 实现方可以忽略它，它不是安全控制。
- ❌ `kid` 可以直接拼文件路径 → 它来自 token，必须先校验再使用。

## 自测

<details>
<summary>1. 为什么 <code>alg</code> 不能信 token 自己写的值？</summary>

因为 header 是 token 的一部分，攻击者可以随意改。服务端若按它声明的算法验证，等于让攻击者决定怎么验证——把 `alg` 写成 `none` 就能跳过签名。
</details>

<details>
<summary>2. <code>none</code> 是合法的算法吗？</summary>

是标准里存在的值，用于「无保护 JWT」，但它在任何需要校验身份的场景都等同于「没有安全保护」。服务端应当把它排除在白名单之外。
</details>

<details>
<summary>3. 改了 header 里的 <code>kid</code>，原来的签名还有效吗？</summary>

无效。签名输入包含 header 的编码值，header 一变，签名就对不上，必须重新签名。
</details>
