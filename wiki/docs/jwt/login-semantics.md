# 登录语义与吊销

> 一句话：JWT 没有「会话」这个概念，每次登录都是**新签一张独立的票**；想让票提前失效，必须自己加状态。

## 登录到底发生了什么

一次登录请求只做两件事：验密码、签发一张新 token。服务端不记录「这个用户登录过几次」，也不存在「续期某个 session」。

```js
// 每次调用都生成新的 jti 和新的 exp
sign({ sub: user.id, jti: crypto.randomUUID(), ver: user.tokenVersion },
     secret, { expiresIn: 60 })
```

所以：**旧票不会因为新登录而失效**，它会一直有效到自己的 `exp`。客户端把本地存储换成新票，只是客户端行为，服务端并不知道旧票被「替换」了。

## 多设备与重复登录

配套实验 `jwt-lab/l2/sessions.mjs` 跑出来的事实：

| 现象 | 结果 |
| --- | --- |
| 两台设备登录 | 两个不同的 `jti`、两个独立的 `exp` |
| 两张票都能访问 | 是，互不影响 |
| 登出设备 A | A 变 401，B 仍是 200 |
| 连续登录 5 次 | 5 张票全部可用，没有并发上限 |

重复登录的代价：

1. **凭证增殖**：每张票都是完整身份，没登记、无法枚举、无法单独回收（除非上 `jti` 黑名单）；
2. **密码哈希被当武器**：每次登录都跑一次故意很慢的 scrypt/argon2，撞库和 DoS 成本被放大；
3. **表达不了「单设备」**：JWT 不自带这个能力，必须加状态；
4. 如果 refresh token 落库，每次登录多一行 session，还要清理。

## 让 token 提前失效的三条路

| 方案 | 失效范围 | 代价 | 适用 |
| --- | --- | --- | --- |
| `jti` 黑名单 | 单个 token | 每请求查一次；条目要保留到该 token 的 `exp` | 单设备登出 |
| `tokenVersion` | 该用户全部 token | 每请求查一次用户 | 改密码、封号、全部设备下线 |
| 短 TTL + refresh | 最多 TTL 秒内失效 | 需要完整的刷新流程 | 标准做法，见后续笔记 |

「同一账号只允许一台设备在线」也在这里实现：登录时先 `tokenVersion += 1` 再签发，其他设备手里的旧版本号立刻失效。粗暴但有效；要精确管理设备，就得建 `sid` + 会话表，每请求查一次。

黑名单的坑：放内存，进程一重启就没了；生产要放 Redis，并给条目设 TTL = token 剩余寿命，否则内存会一直涨。

## claim 是快照

同一个服务里，管理员接口读 token 里的 `role`，个人资料接口则回查数据库——同一个 token，两种数据来源：

- 读 claim：快，但后台改了角色，旧 token 在过期前仍是旧角色；
- 读 DB：实时，但每个请求多一次查询。

没有标准答案，取决于「权限变更要多快生效」和「能接受多少查询」。**敏感操作建议读 DB，展示类信息可以读 claim。**

## 常见误区

- ❌ 用户点了退出，token 就失效了 → 只是客户端删了，服务端仍然认到 `exp`。
- ❌ 改密码会让旧 token 全部失效 → 不会，除非 bump `tokenVersion` 或上黑名单。
- ❌ 多设备登录会互相踢下线 → 不会，每张票独立。
- ❌ JWT 无状态所以不需要存储 → 想要主动吊销就必须存，只是存的东西从「会话」变成了「黑名单/版本号」。

## 自测

<details>
<summary>1. 两台设备，登出其中一台，另一台还能用吗？</summary>

能。登出只把该 token 的 `jti` 拉黑，另一张票的 `jti` 不同，不受影响。
</details>

<details>
<summary>2. 黑名单条目什么时候可以删？永远不删会怎样？</summary>

该 token 过了 `exp` 之后就能删——那时它本来就会被时间校验拒绝。不删会无限增长，且每次请求都要多查一次。
</details>

<details>
<summary>3. 为什么说「单设备登录」不是 JWT 的能力？</summary>

JWT 只负责「票真不真」，不记录「发过几张票」。单设备是业务策略，需要在登录时 bump 版本号或维护会话表才能实现。
</details>
