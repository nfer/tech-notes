# 登录语义与吊销

> 一句话：JWT 没有「会话」这个概念，每次登录都是**新签一张独立的票**；想让票提前失效，必须自己加状态。

## 一次登录只签一张票

一次登录请求只做两件事：验密码、签发一张新 token。

服务端不记录「这个用户登录过几次」，也没有「续期某个 session」这个动作——每次登录都是从零签一张新票，写进 token 的内容在签发那一刻就定死了：

```js
const now = Math.floor(Date.now() / 1000)
// 签进 token 的就是这些 claim
{ sub: user.id, jti: uuid(), iat: now, exp: now + 60 }
```

| claim | 含义 |
| --- | --- |
| `sub` | 这张票代表谁 |
| `jti` | 这张票自己的标识，下一节展开 |
| `iat` | 签发时刻 |
| `exp` | 作废时刻，与 `iat` 相差就是有效时长 |

签发工具一般让你传「有效时长」而不是绝对时刻，但落到 token 里的一定是 `exp` 这个绝对时间戳——`exp` 是协议里的注册名，工具参数不是。

这几项都是签发时的快照。所以**旧票不会因为新登录而失效**，它会一直有效到自己的 `exp`。客户端把本地存储换成新票，只是客户端的动作，服务端并不知道旧票被「替换」了。

## jti：一张票自己的标识

`jti` 是七个注册 claim 之一，全称 **JWT ID**，约定放一个**唯一值**，用来区分「同一个人的不同票」。

为什么需要它：一个人会登录很多次，每次都是一张新票。光靠 `sub` 只能知道「这是谁」，分不清「这是哪一张」。而「退掉手机上的登录、不影响电脑」这种需求，恰恰要求能单独指认一张票。

签发时给它一个随机值就够（UUID 即可），不需要有序、不需要能读出含义。它唯一的作用是让别人能点名某一票。

## 多登录几次会怎样

每张票都有独立的 `jti` 和 `exp`，所以登录两次就是两张互不相干的票，不存在「后一次覆盖前一次」。

配套实验 `jwt-lab/l2/sessions.mjs` 跑出来的事实：

| 现象 | 结果 |
| --- | --- |
| 两台设备登录 | 两个不同的 `jti`、两个独立的 `exp` |
| 两张票都能访问 | 是，互不影响 |
| 登出设备 A | A 变 401，B 仍是 200 |
| 连续登录 5 次 | 5 张票全部可用，没有并发上限 |

这带来四个代价：

1. **凭证增殖**：每张票都是完整身份，服务端没登记、无法枚举、也无法单独回收；
2. **密码校验被当武器**：每次登录都要跑一次故意很慢的密码哈希，撞库和 DoS 的成本被放大，所以登录接口必须限速；
3. **表达不了「单设备」**：JWT 本身没有这个能力，得靠额外状态；
4. **没地方审计**：服务端不知道某个人当前有几张票、分别从哪台设备登录。

## 退出登录，票却还在有效期内

用户点「退出」，期望是下一次请求就被拒绝。但服务端手里没有这张票的副本——token 由客户端保存，服务端每次只是拿密钥重新验算一遍。**没有副本，就没有东西可以「改」。**

改不了已经发出去的票，就只能在验票之外另加一层状态。三种做法的失效范围和代价不同：

### 1. jti 黑名单

登出时把这个票的 `jti` 记进黑名单，之后每次验票都查一遍。

- 失效范围：只有这一张票；
- 代价：每次请求多一次查询；条目要保留到这张票的 `exp` 才能删，否则过期后还得查；
- 存储：放内存重启就丢，生产要放 Redis，并给条目设过期时间。

### 2. 用户版本号

给用户记一个整数版本号，签发时写进票里，验票时和数据库里的当前值比对。想让谁失效就把谁的版本号加一。

- 失效范围：这个人的**所有**票；
- 代价：每次请求多查一次用户；
- 典型用途：改密码、封号、全部设备下线、「同一账号只允许一台设备在线」（登录时先加一再签发，其他设备的旧版本号立刻作废）。

### 3. 短有效期 + refresh token

把 access token 的有效期压到几分钟，另发一个有效期长的 refresh token；过期后客户端拿 refresh 换一张新的 access token。

- 失效范围：最多一个 access token 的有效期；
- 代价：需要一整套刷新流程，refresh token 本身也要存储、轮换和吊销；
- 收益：access token 可以保持无状态，吊销的压力落在 refresh 上。

三种做法不互斥。常见组合是「短 access + refresh」打底，再用版本号兜底「立即全部下线」，黑名单只用于精确到单张票的场景。

## 票没作废，但用户权限变了

还有第三种情况：票没过期、也没被吊销，但用户的角色或资料已经变了。

token 里写下的那些声称（claim，定义见 [claims](/jwt/claims)）——`sub`、`role`、`exp` 等——在签发时被固定下来，之后不会自动跟着数据库走。所以同一个 token，两种数据来源：

- **读 claim**：快，但后台改了角色，旧 token 在过期前仍然带着旧角色；
- **读数据库**：实时，但每个请求多一次查询。

没有标准答案，取决于「权限变更要多快生效」和「能接受多少查询」。敏感操作读数据库，展示类信息读 claim，是常见的折中。

## 常见误区

- ❌ 用户点了退出，token 就失效了 → 只是客户端删了，服务端仍然认到 `exp`。
- ❌ 改密码会让旧 token 全部失效 → 不会，除非提升版本号或上黑名单。
- ❌ 多设备登录会互相踢下线 → 不会，每张票独立。
- ❌ JWT 无状态所以不需要存储 → 想要主动吊销就必须存，只是存的东西从「会话」变成了「黑名单/版本号」。
- ❌ claim 会跟着用户信息更新 → 不会，它是签发那一刻的快照。

## 自测

<details>
<summary>1. 两台设备，登出其中一台，另一台还能用吗？为什么？</summary>

能。登出只把该 token 的 `jti` 拉黑，另一张票的 `jti` 不同，不受影响。
</details>

<details>
<summary>2. 黑名单条目什么时候可以删？永远不删会怎样？</summary>

该 token 过了 `exp` 之后就能删——那时它本来就会被时间校验拒绝，再查黑名单没有意义。不删会无限增长，而且每次请求都要多查一次。
</details>

<details>
<summary>3. 为什么说「单设备登录」不是 JWT 的能力？</summary>

JWT 只负责「票真不真」，不记录「发过几张票」。单设备是业务策略，需要在登录时提升版本号或维护会话表才能实现。
</details>

<details>
<summary>4. 用户被降级成普通用户，但他手里的旧 token 还写着管理员，服务端怎么处理？</summary>

要么每次请求回查数据库里的当前角色（实时，多一次查询），要么把 token 有效期缩短到可接受的延迟。只信 token 里的 `role` 会出现「降权后仍能操作」的窗口期。
</details>
