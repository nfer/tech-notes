# JWT 实验课 · Lesson 1：三段结构与签名

## 本课要建立的三个结论

1. **JWT 是「签名 + 明文」，不是加密。** 三段都是 base64url，任何人拿到都能解码看内容。
2. **签名只覆盖前两段**（`header.payload` 原样拼接后做 HMAC），不覆盖签名段本身，也不覆盖任何"服务端状态"。
3. **验签通过 ≠ token 可用。** 验签只回答"内容有没有被改、是不是我签的"，不回答"过没过期、是不是签给本服务的、有没有被吊销"。

## 文件

| 文件 | 作用 |
| --- | --- |
| `lib/jwt.mjs` | 手写 HS256 签发/验签（零依赖，只用 `node:crypto`） |
| `01-anatomy.mjs` | 解剖三段、打印签名输入、对比正确/错误 secret |
| `02-tamper.mjs` | 改 payload 的 role / 改 exp，观察签名失效；对比"不验签的服务端" |
| `03-alg-none.mjs` | 伪造 `alg:none`，打穿一个天真实现 |
| `04-claims.mjs` | 签名有效但过期 / aud 不对 / 已吊销，三种"不可用" |

运行（本机 PATH 没有 node，`run` 里写死了运行时自带的 Node 24）：

```bash
cd jwt-lab
./run 01-anatomy.mjs
```

## 实验步骤：先预测，再运行

**每一小步都先写下你的预测，再跑。预测错了才是学到东西的时刻。**

1. 跑 `01-anatomy.mjs`。回答：`signature` 段是 32 字节，那它编码前是什么？为什么长度固定？
2. 打开 `01-anatomy.mjs`，把 `expiresIn: 3600` 改成 `-10`（已过期），跑。观察 `verifySignature` 是否仍然 `ok: true`。这说明什么？
3. 跑 `02-tamper.mjs`。然后自己加第三种篡改：把 `sub` 改成别人的用户 id，先预测结果。
4. 跑 `03-alg-none.mjs`。然后改一下 `vulnerableVerify`，让它同时拒绝 `alg:"none"` 和接受 `alg:"HS256"`，验证伪造 token 被拦。
5. 跑 `04-claims.mjs`。重点看第一段输出：签名合法的过期 token。

## 课后问题（在对话里回答，答完进 Lesson 2）

- **Q1** JWT 为什么设计成"签名 + 明文"而不是加密？加密不是更安全吗？
- **Q2** 用户点了「退出登录」，你要让那个已经发出去的 JWT 立刻失效，怎么做？代价是什么？
- **Q3** 微服务场景：A 服务签发、B 服务验签。B 需要拿到什么？谁该持有签名密钥？如果 B 被攻破，攻击者能干什么？

## 什么时候该用现成的库

生产环境用 `jose`（推荐）或 `jsonwebtoken`，不要手写。不是签名算不对，而是库帮你处理了：算法白名单、`exp/nbf` 校验、`aud/iss` 校验、时钟偏移、`kid` 选钥、JWK/JWKS 解析、各种历史 CVE 的边界情况。手写版本的价值是让你在 `jose` 报错时知道它在报什么。
